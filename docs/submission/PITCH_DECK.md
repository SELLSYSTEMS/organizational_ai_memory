## Appendix A - Four Enforcement Planes

1. Application identity: human, agent, and workload principals.
2. Policy: department, template, sponsor ceiling, and explicit denials.
3. Runtime identity: locked Linux agent, systemd sandbox, private workspace.
4. Data authority: FORCE RLS, fixed views, and brokered grants.

**Important:** the MVP does not claim a Linux or PostgreSQL account per human.

## Appendix B - Threat Boundary

Trusted administrators: host root and PostgreSQL superuser.

Proved for ordinary workloads:

- protected repository and installed source denied
- application and model credentials denied
- outbound IP socket denied
- direct PostgreSQL denied
- own private workspace allowed
- only consented current revision returned through the broker

## Appendix C - Deterministic vs Spark

| Deterministic authority | Optional Spark adaptation |
| --- | --- |
| selects approved records | rewrites within selected records |
| retains stored plan | returns strict structured steps |
| defines allowed citations | citations validated before display |
| remains available on failure | non-authoritative and rate limited |

## Appendix D - Governance Boundary

```text
quarantined source
-> sealed bytes
-> service candidate
-> independent reviewer approval
-> architect draft promotion
-> canonical write denied
```

## Appendix E - Deployment + Known Gaps

Next deployment steps:

- enterprise SSO/SCIM replacing root-managed human credential context
- container-runtime adapters preserving distinct agent identity
- controlled ingestion connectors
- acceptance/outcome events and time-series capability analytics

Not claimed today: autonomous canonical publication, measured ROI, digital
twins, autonomous duplicate detection, or a complete enterprise connector set.
